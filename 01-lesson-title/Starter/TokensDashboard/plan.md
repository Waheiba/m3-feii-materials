# Feature Plan Template

Use this completed example as the target shape for the Module 3 development plan. Students can adapt the structure while following the lessons, but the example is filled in for the AI Usage Insights feature so it is usable without guessing what belongs in each section.

## Feature name

AI Usage Insights

## Feature summary

Add a team-level insights screen to the Tokens Dashboard app. The feature surfaces cautious review signals from the app's existing mock data so a team lead, engineering manager, or project lead can review model usage, token investment, and delivery trends before changing team guidance.

The app does not call an LLM at runtime. Insights are generated by deterministic local rules over existing stores.

## Audience

- Team lead
- Engineering manager
- Project lead or project manager

## Goals

- Add one new summary row that opens the AI Usage Insights screen.
- Show compact team-level insight cards.
- Explain why each insight appeared.
- Provide a suggested human review step.
- Include a caveat that prevents overinterpretation.
- Keep the feature deterministic, local, and explainable.

## Non-goals

- Do not implement the feature during Module 3.
- Do not call an LLM from the iOS app.
- Do not add networking, persistence, authentication, or a backend.
- Do not add a tab bar or large navigation redesign.
- Do not add per-insight detail screens in v1.
- Do not expose individual developer names in insight cards.
- Do not claim that AI caused delivery improvements.
- Do not classify models as premium, standard, or cheap unless that metadata exists.

## User flow

```text

  -> tap "AI Usage Insights"
UsageInsightsView
  -> review team-level insight cards
```

## UI plan

Add one new row to the existing summary screen.

Summary row copy:

```text
AI Usage Insights
5 team-level review signals found for May 2026. Review model concentration, token investment, and delivery trends before changing team guidance.
```

The insights screen should include:

- Title: `AI Usage Insights`
- Subtitle: `May 2026 - Team-level review signals`
- Caution note: `These insights are review prompts, not automatic conclusions. Interpret token usage alongside task complexity, quality, and delivery context.`
- A vertical list of compact cards.

Each card should show:

- Category label
- Severity/status label
- Title
- Supporting metric
- Short explanation
- Suggested next step
- Caveat

## Rules or business logic

Describe any deterministic rules the feature needs. Avoid vague instructions like "use AI to decide."

- Model usage concentration: create an insight when the top model accounts for more than 40% of month-to-date spend.
- Model usage increase: create an insight when any model has a month-over-month increase above 15%.
- Delivery trend signal: create an insight when the AI-heavy cohort's ticket-to-merge trend improves meaningfully over the trailing period.
- Workflow pattern review: create a contested insight when an anonymized workflow pattern shows above-median token usage with below-median merged PR output.
- Data-quality guardrail: show a cautious data-quality state when required data is empty, stale, or below the minimum useful sample size.
- Screen-level caution: always remind the user that insights are review prompts, not automatic conclusions.

## Edge cases

- Empty model list
- Zero total spend
- Missing or zero token totals
- Missing month-over-month change values
- Empty developer outcome list
- Too few developer outcomes to compare medians responsibly
- Empty ticket-to-merge samples
- Only one AI usage cohort available
- Negative or impossible metric values
- Duplicate insight IDs or titles
- Insight copy that exposes individual names
- Insight copy that implies causation instead of correlation
- Insight copy that sounds like employee performance evaluation

## Accessibility requirements

- Cards must be readable with VoiceOver.
- Category and severity labels must be included in accessibility text.
- Supporting metrics must be spoken clearly.
- Caution text must not be communicated through color alone.
- The insights list must support Dynamic Type.
- The screen must remain useful without relying on chart visuals.

## Acceptance criteria

- The summary screen has one new AI Usage Insights row.
- Tapping the row opens one new insights screen.
- The insights screen displays compact team-level cards.
- No insight includes individual developer names.
- No insight says AI caused a delivery improvement.
- No insight depends on premium or cheap model classification.
- The service generates insights from local mock stores only.
- Empty or insufficient data produces a cautious data-quality state.
- The planned code surface is small enough for a later implementation lesson or module.

## Open questions

Use this section for decisions that still require human review.

- Should the anonymized workflow-pattern insight ship in v1, or should it be deferred because it may still be inferable from the named chart data?
- Should severity labels use `informational`, `review`, and `watch`, or should the UI avoid severity language entirely?
- Should the insight cards link back to the existing chart screens, or should v1 keep the insights screen read-only?
- What minimum sample size is acceptable before showing workflow-pattern insights?
- Should the summary row show the number of insights found, or use a more stable phrase such as "Team-level review signals available"?
